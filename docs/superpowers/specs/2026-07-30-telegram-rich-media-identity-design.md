# Telegram: медиа, личности и инструменты

Дата: 2026-07-30
Статус: утверждён владельцем, готов к планированию

## Задача

Бот Persona в Telegram:

1. Утекает служебные блоки промпта в текст ответа.
2. Не различает участников чата и зовёт владельца `Empty`.
3. Обещает отправить стикер/фото/видео, но не отправляет.
4. Не ходит в интернет, хотя инструменты для этого написаны.
5. Не может поставить MCP-сервер по просьбе владельца.

Общая причина у пунктов 1-2 и частично 4 — кампания «ultra compact»
(коммиты `eb0a4fe`, `dbcc492`), которая ради скорости обрезала промпт,
контекст и вывод. Часть обрезок уже снята в `555bc83` (лимит токенов);
эта спека снимает остальные и достраивает недостающее.

## Что уже есть и переиспользуется

Существенная часть функциональности написана и заперта флагами:

## Срез 1 — Утечка служебных блоков

### Проблема

Модель воспроизвела в чат содержимое `<TRUSTED_TELEGRAM_IDENTITY>`:
`AUTHORITATIVE CURRENT TELEGRAM TURN: - current_message_author_id=...`.
Блок вклеивается в системный промпт в `app/adapters/conversation/legacy.py:228`.
`persona_only_reply` такое не ловит: там разбор реплик по говорящим, а не
поиск служебной разметки.

### Решение

В `app/integrations/telegram/output_guard.py` — новая функция
`strip_internal_markup(text) -> str`, вызывается первой в `persona_only_reply`:

- удаляет парные и непарные теги `<TRUSTED_TELEGRAM_IDENTITY>`,
  `<TRUSTED_PERSONA_STYLE>`, `<UNTRUSTED_*>`, `<GROUP_RULES>` вместе с содержимым;
- удаляет строки, начинающиеся с `AUTHORITATIVE CURRENT TELEGRAM TURN`,
  `SERVER-VERIFIED TELEGRAM IDENTITY`, `- current_message_author_`,
  `- sole_owner_creator_id`, `Only Telegram user_id=`;
- удаляет `<tool>`-разметку, если она просочилась в текст ответа.

Если после чистки не остаётся ничего осмысленного, ответ считается
непригодным и не отправляется — молчание лучше огрызка.

Плюс строка в `_TELEGRAM_RULES` и `_GROUP_REPLY_SYSTEM`: содержимое
служебных тегов — это данные для рассуждения, а не текст для отправки.
Промпт здесь страховка; защита — гвард.

## Срез 2 — Личности участников и редактирование на сайте

### Проблема

`identity_context()` собирает корректный справочник: numeric id как источник
истины, владелец по привязке, до 40 участников чата, отдельно недоверенные
утверждения самого человека. Затем блок режется **дважды**:

- `app/integrations/telegram/service.py:105` — `[:2_000]`
- `app/adapters/conversation/legacy.py:229` — `[:2_000]`

JSON с участниками длиннее 2 000 символов, поэтому заголовок выживает,
а `people_seen_in_this_chat` обрывается на середине. Ambient-ветка получает
16 000 и различает людей заметно лучше — это подтверждает диагноз.

Дополнительно `_bounded_transcript` в `legacy.py:240` даёт Telegram
800 символов истории (4-5 реплик), поэтому «кто что сказал» теряется.

Проверка по базе (`C:\Users\Yaroslav\.persona\persona.db`):

```
telegram_user_id=2133993638 username=YaroslavEmpty first_name='Empty'
display_name='Empty' is_owner=1 message_count=83
```

Привязка владельца работает. `Empty` — реальное `first_name` профиля
владельца в Telegram, другого имени у бота нет.

### Решение

Лимиты:

- `service.py` и `legacy.py`: `2_000` → `12_000`;
- транскрипт Telegram: `800` → `6_000`.

Редактирование на `/settings/telegram-people`. Новая таблица
`telegram_person_override` (владелец — доверенный источник, в отличие от
`telegram_person_fact`, который собирается из слов самого участника):

| Поле | Смысл |
|---|---|
| `display_name_override` | как Persona зовёт человека; перекрывает имя из Telegram |
| `note` | роль или указание: «брат», «коллега», «не воспринимать всерьёз» |
| `ignored` | бот не реагирует на этого участника |

POST-эндпоинты в `app/web/routes/telegram_people.py`:

- `POST /settings/telegram-people/{telegram_user_id}` — сохранить имя, заметку, флаг игнора;
- `POST /settings/telegram-people/{telegram_user_id}/owner` — назначить владельцем.

Назначение владельца перепривязывает `owner_telegram_user_id` в настройках
Telegram и снимает флаг со всех остальных в одной транзакции — инвариант
«ровно один владелец» уже поддерживается в `observe_message`.

`identity_context()` применяет override поверх данных из Telegram и
помечает заметки владельца как доверенные, отдельно от
`untrusted_remembered_claims_by_current_sender`. Разделение доверия
сохраняется — это несущая часть защиты от подмены личности.

## Срез 3 — Медиа из интернета и стикеры

### Проблема

`actions.py:204` разрешает `media_ref` только как `attachment:N` или
HTTPS-ссылку, дословно встреченную в сообщении пользователя. Промпт прямо
запрещает: `Never invent a URL`. Модель не может подставить найденную ссылку,
поэтому говорит «вот стикеры» и не отправляет ничего.
`_OWNER_PRIVATE_KINDS` (`actions.py:144`) дополнительно запрещает любое
медиа вне лички владельца.

### Решение

Новый модуль `app/integrations/telegram/media_resolver.py` — одна функция
`resolve_media(url, expected_kind) -> ResolvedMedia | None`:

1. `_url_is_safe()` из `app/mcp/builtin_tools.py` — SSRF-защита уже написана;
2. HEAD-запрос: `content-type` обязан соответствовать типу
   (`image/*` для photo, `video/*` для video, `image/gif` или `video/mp4`
   для animation), `content-length` в лимитах Telegram (10 МБ фото, 50 МБ видео);
3. несоответствие или таймаут — `None`, действие отменяется.

Ключевой инвариант: **если медиа не отправилось, бот не утверждает, что
отправил.** При `None` действие снимается, и ответ идёт текстом.

`_OWNER_PRIVATE_KINDS` снимается: медиа разрешено и в группах, но только
после проверки. Промпт меняется с «Never invent a URL» на «ссылку бери из
результатов `web_search`; не выдумывай URL по памяти».

### Стикеры

В Bot API нет поиска стикеров: отправить можно по `file_id` или через
`getStickerSet` для пака с известным именем.

Новая таблица `telegram_sticker`: `file_id`, `emoji`, `set_name`,
`seen_count`, `last_seen_at`. Наполняется двумя путями:

- автоматически — каждый входящий стикер в любом наблюдаемом чате
  записывается вместе со своим `emoji` (Telegram отдаёт его в объекте стикера);
- по требованию — владелец добавляет имена паков в настройках, транспорт
  тянет их через `getStickerSet`.

Модель **не выбирает `file_id`** — она их не знает и не должна знать. Она
возвращает эмоцию (`"sticker_emoji": "😂"`), транспорт сам выбирает стикер
с этим эмодзи, предпочитая часто виденные в этом чате. Побочный эффект —
модель физически не может отправить произвольный файл.

Эмодзи в тексте работают уже сейчас: это обычный UTF-8, отдельной работы
не требуют. Реакции на сообщения тоже работают (`actions.py:47`).

## Срез 4 — Интернет и инструменты в Telegram

### Проблема

`worker.py:573`: `allow_tools = private_owner and _owner_tools_needed(text)`.
Эвристика (`worker.py:1014`) включает инструменты по списку ключевых слов
либо при длине текста больше 160 символов. «Найди фото кота» — 15 символов,
ключевого слова нет, инструменты выключены.

### Решение

`_owner_tools_needed` удаляется. Доступ определяется политикой:

- личный чат владельца — полный набор инструментов;
- группа — только чтение (`web_search`, `web_browse`, `fetch_json`),
  без файловых операций, shell и установки чего-либо;
- не владелец — инструментов нет.

Стоимость промпта (схемы инструментов) принимается: за скорость уже
заплатили обрывами и потерей контекста, второй раз платить не будем.

## Срез 5 — MCP и shell по кнопке

### Угроза

`install_mcp` регистрирует произвольную команду запуска, `run_shell` и
`run_mac` её исполняют. Вход модели включает недоверенный текст участников
группы. Автоматическая установка по решению модели даёт путь
инъекция → выполнение кода на машине владельца. То, что служебные блоки
уже утекали в вывод (срез 1), показывает: граница доверия здесь дырявая.

### Решение

Из групп — запрещено полностью, независимо от того, кто просит.

Из лички владельца — двухшаговое подтверждение. Новая таблица
`telegram_pending_action`: `id`, `persona_user_id`, `tool_name`,
`args_json`, `created_at`, `expires_at` (TTL 15 минут), `consumed_at`.

1. Модель вызывает `install_mcp`; вместо выполнения создаётся запись.
2. Бот шлёт карточку: имя сервера, **точная команда запуска**, источник —
   и inline-кнопки «Установить» / «Отмена».
3. Callback принимается только от владельца, только по `id` записи.
   Аргументы читаются **из базы, а не из callback_data** — иначе кнопку
   можно подделать. Запись одноразовая, помечается `consumed_at`.
4. Просроченное подтверждение не выполняется.

Тот же механизм используется для `run_shell` из Telegram.

## Тестирование

- `output_guard`: служебные теги и заголовки вырезаются; ответ, состоящий
  только из служебного блока, даёт пустую строку и не отправляется.
- `identity_context`: блок с 40 участниками доезжает до промпта целиком;
  override имени применяется; заметки владельца отделены от недоверенных
  утверждений участника.
- `media_resolver`: приватный адрес, неверный `content-type`, превышение
  размера и таймаут дают `None`; корректный URL проходит.
- `telegram_sticker`: подбор по эмодзи, предпочтение часто виденных,
  пустая база не роняет ответ.
- `telegram_pending_action`: чужой callback отклоняется, просроченный
  отклоняется, повторное нажатие не выполняет действие второй раз,
  подделанные аргументы в callback_data игнорируются.
- Групповой чат: попытка установки MCP отклоняется независимо от
  формулировки просьбы.

## Порядок работ

Срезы независимы и идут по возрастанию риска: 1 → 2 → 3 → 4 → 5.
Каждый — отдельный коммит с бампом `__version__` и `CACHE_VERSION`,
пуш в master.

## Сознательно не делается

- Скачивание медиа на диск — Telegram забирает файл по URL сам.
- UI управления стикерпаками сложнее одного поля со списком имён.
- Изменения в `run_mac` — очередь на устройстве уже имеет свой блок-лист.
- Произвольная установка MCP без подтверждения — отклонено как путь к RCE;
  функциональность для владельца сохранена через кнопку.

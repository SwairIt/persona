# Контент-план Persona: семантическое ядро, блог-платформа, 300+ статей

Дата: 2026-08-25. Автор плана: оркестратор + разведка по коду.
Статус: **черновик на утверждение владельцем**, реализация не начата.

---

## 0. Зачем и честная рамка

Задача владельца: «хочу быть в топе по всем словам про ИТ, локальные модели,
Hermes, приватность, продуктивность», 300+ статей, блог с категориями и поиском,
статья с прогрессом чтения и липким оглавлением.

**Что я обязан сказать прямо.** 300 статей, написанных по одному шаблону, — это
не путь в топ, а риск для всего домена: поисковики оценивают полезность, и массив
однотипных текстов тянет вниз в том числе те страницы, которые могли бы
ранжироваться. Поэтому план построен так:

- **кластеры вместо россыпи** — 12 тематических кластеров, у каждого одна
  «столповая» статья и 15–30 спутников, все связаны перекрёстными ссылками;
- **у каждой статьи свой угол и своя фактура** — реальные команды, требования к
  железу, цены и лимиты провайдеров, таблицы сравнения, замеры. Никакой воды;
- **правило правдивости** (выстрадано 2026-08-24/25): ни одного обещания, которого
  продукт не держит. В блоге Persona уже есть сильная и редкая конвенция —
  в каждом сравнении обязателен раздел «где конкурент объективно лучше» и
  добровольное признание неудобных фактов. Она сохраняется во всех новых текстах;
- **длина по теме, а не по норме** — владелец явно сказал не выравнивать время
  чтения. Пилларам 2000–4000 слов, спутникам 700–1500, справочникам 300–600.

## 1. Что уже есть (проверено по коду, не по памяти)

**Движок:** `app/blog.py` (170 строк) — загрузка markdown из
`app/web/content/blog/*.md`, самописный парсер front matter (НЕ YAML), рендер
через `markdown-it-py` (commonmark + table + strikethrough, typographer),
`lru_cache(maxsize=1)`, `list_posts()/list_categories()/get_post()/reload_posts()`.

**Уже работает:** время чтения (`_WPM = 170`), оглавление (h2/h3 → `TocItem`),
прогресс-бар чтения, скроллспай на IntersectionObserver, фильтр категорий
(клиентский), связанные статьи (та же категория, 3 шт.), prev/next по дате,
хлебные крошки, JSON-LD `Blog` и `BlogPosting`, секция «Из блога» на лендинге
(`home-blog`, 3 поста).

**28 статей**, 8 категорий: Основы, Память, Приватность, Продуктивность, Своя
модель, Сравнения, Гайды, Технологии.

**Чего нет:** поиска, пагинации, страниц категорий и тегов (теги парсятся, но
нигде не выводятся и не индексируются), RSS, `FAQPage`/`BreadcrumbList`/`Article`
разметки, og:image у статей, даты обновления, горячей перезагрузки контента,
тестов на блог и sitemap.

**Ограничения, которые нельзя нарушить:**
- CSP: внешние скрипты запрещены (кроме Яндекс.Метрики), шрифты — только Google
  Fonts. Report-Only политика уже целится в `script-src 'self'` — значит новый
  JS кладём файлами в `/static/`, а не инлайном.
- Публичные страницы — **хардкод по-русски**, без `t()`. Это конвенция.
- Роут-бюджет `REGISTERED_ROUTE_BUDGET = 1157`, запаса нет: каждый новый роут
  требует пере-замера на живом приложении и обоснования в комментарии.
- Роут-модули не должны импортировать `get_connection` напрямую.
- Два несовместимых дизайна: блог на `landing/style.css` (v1: фиолетово-циановый
  градиент, стекло, Inter, радиус 22px), лендинг на `landing_v2/style.css`
  (v2: iris/lavender, rim-light вместо теней, Space Grotesk, радиус 16px).

**Решение по дизайну (требует подтверждения):** привести блог к v2, чтобы сайт
выглядел одним продуктом. Это переписывание `blog.css` под токены v2 — работа на
несколько часов, но иначе переход с лендинга в блог визуально ломает впечатление.

## 3. Работы по платформе (до контента)

### 3.1. Движок `app/blog.py`
- **Front matter → YAML** (или строгий парсер): сейчас самописный, кавычки в
  заголовке не снимаются и утекают в вывод. С 300 статьями это станет заметно.
- **Новые поля:** `updated` (дата обновления → `dateModified`), `image`
  (og:image), `author`, `featured`, `noindex` (для служебных), `related`
  (явные slug'и вместо «та же категория»).
- **Слаг-якоря вместо позиционных.** Сейчас `id="sec-1"` по порядку — вставил
  заголовок, и все внешние ссылки на якоря сломались. Делаем транслит-слаги
  с дедупликацией.
- **Индекс для поиска**: при загрузке строим инвертированный индекс по
  заголовкам/подзаголовкам/тексту (без внешних зависимостей), плюс
  `_search(query)` с ранжированием по вхождениям в заголовок/тело.
- **Горячая перезагрузка**: `reload_posts()` уже есть, но не вызывается —
  повесить на owner-эндпоинт и на изменение mtime каталога.
- **Производительность**: 345 файлов парсить лениво при первом обращении
  приемлемо, но `/blog` и `/sitemap.xml` получат холодный старт в секунды —
  добавить прогрев при старте в фоне и кэш HTML на диске.

### 3.2. Роуты (пере-замер бюджета обязателен)
- `GET /blog` — пагинация (по 24), фильтр по категории через query, поиск.
- `GET /blog/category/{slug}` — **индексируемые** страницы категорий (сейчас
  фильтр только клиентский, для поисковика их не существует).
- `GET /blog/tag/{slug}` — страницы тегов.
- `GET /blog/search?q=` — серверный поиск (работает без JS), + JSON для живого
  поиска на странице.
- `GET /blog/rss.xml` и `/blog/atom.xml` — фиды + `<link rel="alternate">`.
- Все новые пути — в `_PUBLIC_PREFIXES` и в `_STATIC_PUBLIC_PATHS` sitemap.

### 3.3. Микроразметка (самый дешёвый рост в выдаче)
- `Article`/`TechArticle` вместо голого `BlogPosting`, с `dateModified`,
  `wordCount`, `image`, абсолютными URL.
- `BreadcrumbList` — крошки уже нарисованы, разметки нет.
- **`FAQPage`** — в статьях уже есть блоки «## Частые вопросы» с `###`-вопросами;
  автоматически превращать их в разметку. Это прямой шанс на расширенный сниппет.
- `HowTo` для гайдов с нумерованными шагами.
- `ItemList` на страницах категорий.
- `WebSite` + `SearchAction` на главной.

### 3.4. Шаблоны
- `blog_index.html`: поиск (форма + живой фильтр), пагинация, категории как
  ссылки, теги, сортировка, пустое состояние поиска.
- `blog_post.html`: og:image и twitter:card, дата обновления, теги под статьёй,
  кнопки «поделиться» (без внешних скриптов), «читать далее» по тегам, якорь на
  каждый заголовок (кликабельная решётка).
- Оглавление: уже липкое и со скроллспаем — добавить прогресс внутри оглавления
  и сворачивание на мобильных (сейчас на узком экране правая колонка уезжает).
- Новый шаблон страницы категории и тега.

## 4. Производство контента (основной объём)

**Волнами по кластерам**, чтобы перекрёстные ссылки внутри кластера были
осмысленными, а не случайными.

Порядок: 2 (локальные модели) → 3 (выбор модели) → 5 (агенты/Hermes) → 7
(провайдеры) → 10 (self-host) → 4 (память) → 1 (личный ИИ) → 6 (приватность) →
8 (продуктивность) → 9 (сравнения) → 11 (дообучение) → 12 (глоссарий).

Мотив порядка: сначала кластеры с наибольшим поисковым спросом и наименьшей
зависимостью от продукта — они приводят аудиторию, которая потом читает
продуктовые сравнения.

**Правила для каждой статьи** (в стайл-гайде, проверяются тестом):
1. Уникальный угол — в карте контента у каждой статьи записан свой тезис;
2. Минимум одна таблица, список шагов или блок кода с реальными командами;
3. 5–7 внутренних ссылок, описательный анкор, никаких «здесь»;
4. Блок «## Частые вопросы» с 4–8 вопросами → идёт в `FAQPage`;
5. Для сравнений — обязательный раздел «где конкурент лучше»;
6. Ни одного непроверяемого утверждения о продукте;
7. Front matter заполнен целиком, включая `updated` и `image`.

**Контроль качества** (автотесты, а не глазами):
- ни одного дубля заголовка/slug;
- сходство текстов ниже порога (шинглы) — ловим шаблонную генерацию;
- все внутренние ссылки ведут на существующие статьи или живые страницы;
- front matter валиден, дата не в будущем;
- запрещённые формулировки («данные не покидают устройство», «открытый код»,
  «ноль телеметрии») отсутствуют;
- у каждой статьи есть FAQ и хотя бы одна таблица/список/код.

## 5. Техническое SEO

- Абсолютные canonical (сейчас корне-относительные) + глобал `base_url`.
- og:image: генерировать статические обложки под каждую статью нельзя без
  внешних сервисов (CSP), поэтому — набор из ~12 категорийных обложек в
  `/static/blog/og/` + поле `image` для исключений.
- robots.txt: сейчас разрешено всё, включая кабинет. Добавить `Disallow` для
  `/chat`, `/settings`, `/root`, `/api` — гейт их и так закрывает, но краулер
  тратит бюджет.
- sitemap: разбить на индекс + отдельные карты (страницы, блог, категории,
  теги) — 345 статей в одном файле ещё влезают, но расти дальше некуда.
- Внутренняя перелинковка: автоматический блок «Читать по теме» на основе
  пересечения тегов, а не только категории.
- Скорость: холодный `/blog` с 345 статьями — измерить и, если нужно,
  прекомпилировать HTML на диск.
